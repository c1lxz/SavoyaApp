# Роли сотрудников и опросы — подготовка обновления 1.6.0

Документ описывает код выпуска 1.6.0 (Android versionCode 17) и порядок его
проверки. Он не подтверждает развёртывание на сервере, сборку APK или доставку
уведомлений. Базовая настройка новостей, медиа, Nginx, Firebase и подписи APK
описана в [NEWS.md](NEWS.md). Указанные там результаты проверки сервера относятся
к 25–26 сентября 2026 года; перед обновлением нужно проверить актуальное состояние.

## Права доступа

| Действие | Житель | Диспетчерская | Администрация |
| --- | --- | --- | --- |
| Читать новости и голосовать | Да | Да | Да |
| Публиковать, менять и удалять новости, загружать медиа | Нет | Нет | Да |
| Создавать, менять и закрывать опросы | Нет | Нет | Да, с ограничениями ниже |
| Смотреть жителей, пропуска и монитор событий | Нет | Да | Да |
| Удалять пропуска, блокировать/разблокировать/удалять жителей | Нет | Да | Да |
| Создавать жителей | Нет | Нет | Да |
| Смотреть и создавать сотрудников | Нет | Нет | Да |
| Менять роль сотрудника, блокировать/разблокировать сотрудника | Нет | Нет | Да, с ограничениями ниже |
| Удалять сотрудников | Нет | Нет | Нет |

Для создания жителя нужны номер телефона и номер участка. Сотрудник создаётся с ролью
`administration` или `dispatcher`; телефон и участок необязательны. В рабочей SQLite
колонка `users.phone` обязательна и уникальна, поэтому сотрудник без телефона получает
в ней внутренний идентификатор `@staff:…`. API и интерфейс показывают пустой телефон;
идентификатор нельзя передавать в Gate как номер. Автоматическое создание
пропуска жителя в Gate для сотрудника не выполняется. При открытии точки доступа
сотрудник без телефона использует уже настроенный Gate-ключ активной администрации;
действие записывается с ID и логином самого сотрудника. Если этот ключ недоступен,
открытие возвращает ошибку и новый телефонный ключ не создаётся. Смена роли применяется только к
существующим сотрудникам: endpoint не превращает жителя в сотрудника.

Нельзя понизить собственную роль или заблокировать себя. Нельзя отключить либо
понизить последнего активного администратора. Проверка выполняется под блокировкой
БД с повторной проверкой прав инициатора: два администратора не должны одновременно
лишить систему всех активных администраторов. Удаление через административный API
доступно только для жителей.

Старый `is_admin` сохраняется для совместимости. При `is_admin=false` роль
сотрудника отсутствует. Старый администратор с `staff_role=NULL` считается
администрацией; явное неизвестное значение прав не даёт. Права сервер проверяет
по актуальной записи пользователя при каждом запросе. Клиент скрывает недоступные
действия, но источником прав остаётся сервер.

Старый APK может показывать административные кнопки диспетчеру, поскольку он
понимает только `is_admin`; запрещённые операции сервер отклонит. Для правильного
интерфейса ролей необходим новый клиент. Старый клиент не отображает опросы:
новость только с опросом может выглядеть пустой. Учитывайте это при переходе
жителей на новую версию.

## Правила опросов и API

В новости возможен один опрос: вопрос от 1 до 300 символов, от 2 до 10 вариантов
по 1–200 символов. Крайние пробелы удаляются. Повторяющиеся варианты с учётом
регистра, Unicode-нормализации и пробелов отклоняются. Новость может содержать
только опрос либо опрос вместе с текстом и вложениями.

Один аккаунт имеет один текущий ответ. Пока опрос открыт, выбор можно заменить;
повтор того же запроса не добавляет голосов. Администрация закрывает опрос,
повторное закрытие безопасно. Возобновления закрытого опроса нет.

Вопрос, варианты и удаление опроса доступны только до первого голоса и до
закрытия. После первого голоса сохраняется `started_at`: даже удаление всех
проголосовавших аккаунтов не разблокирует изменение определения опроса. Текст и
вложения новости менять можно. Сохранение точно такого же определения не меняет
варианты или голоса. Изменение вопроса/вариантов до голосования создаёт новые ID
вариантов, поэтому устаревший выбор клиента не попадёт в другой вариант.

Ответ API содержит суммы по вариантам и собственный выбор пользователя. Имена
и списки проголосовавших не выдаются. Это анонимность результатов для клиентов,
а не отсутствие связи в БД: таблица голосов хранит `user_id`, необходимый для
ограничения одного ответа и его замены. После удаления аккаунта его голоса
удаляются; суммы уменьшаются, а запрет изменения опроса сохраняется.

Создание через `POST /api/news` дополнительно принимает:

```json
{
  "text": "",
  "media_ids": [],
  "request_id": "unique-request-id",
  "poll": {
    "question": "Что улучшить в первую очередь?",
    "options": ["Освещение", "Дороги"]
  }
}
```

`PUT /api/news/{post_id}` использует прежнюю `version`. Если поле `poll` опущено,
опрос сохраняется; `poll: null` пытается удалить его; объект меняет определение
с указанными ограничениями. Пустая новость без текста, вложений и опроса недопустима.
Исторический хеш идемпотентной публикации без опроса сохраняется: повтор старого
запроса с тем же `request_id` не создаёт новый пост.

| Запрос | Результат |
| --- | --- |
| `POST /api/news/{post_id}/poll/vote`, `{"option_id": 10}` | Объект опроса, HTTP 200 |
| `POST /api/news/{post_id}/poll/close`, без тела | Объект опроса, HTTP 200 |

Объект `poll` содержит `id`, `question`, `options` (`id`, `text`, `votes`),
`total_votes`, `my_option_id`, `is_closed`, `closed_at`, `can_edit`.
`can_edit` описывает состояние опроса; право администрации проверяется отдельно.
В новостях без опроса возвращается `poll: null`. Голос в закрытый опрос — 409,
неподходящий или устаревший ID варианта — 422, удалённая новость — 404.

Изменение, голосование, замена голоса и закрытие не создают push-уведомления.
Уведомления создаются при первоначальной публикации новости. Голосование и
закрытие не меняют `version` новости и не конфликтуют с открытым редактором
текста. Мутации опроса, изменение и удаление поста используют общую блокировку
родительской записи. Для страницы архива опросы и суммы читаются двумя запросами,
без отдельного запроса на каждую новость.

## Изменения БД и сохранение сессий

При старте добавляются отсутствующие nullable-столбцы `users.staff_role`
(`VARCHAR(24)`) и `users.auth_generation` (`VARCHAR(32)`). Существующим
`is_admin=true AND staff_role IS NULL` назначается `administration`; явные роли
сохраняются. Существующим аккаунтам `auth_generation` не заполняется: их старые
JWT без этого поля продолжают работать до обычного окончания срока действия.

Новые аккаунты получают случайный `auth_generation`; такое же значение входит
в JWT. Сервер сравнивает значение JWT с БД. Если SQLite повторно использует ID
удалённого аккаунта, его старый JWT не подойдёт новому аккаунту. Все внешние
скрипты создания пользователей также должны использовать этот механизм, а не
вставлять новые аккаунты с `auth_generation=NULL`. Не обнуляйте поколения и не
заполняйте их массово у старых аккаунтов при обновлении.

Добавляются таблицы `news_polls`, `news_poll_options`, `news_poll_votes`.
Старые таблицы новостей, пропусков и Gate не заменяются. Первичный ключ голоса —
пара `(poll_id, user_id)`; составной внешний ключ связывает вариант с его опросом.
ID удалённых вариантов не переиспользуются SQLite благодаря `AUTOINCREMENT`.

`create_all` создаёт отсутствующие таблицы, но не изменяет уже существующие.
Если устанавливалась ранняя тестовая схема опросов, до запуска проверьте колонки,
индексы и ограничения, включая `news_polls.started_at`. Для ранней SQLite-таблицы
без этого поля нужна отдельная миграция `ADD COLUMN started_at DATETIME NULL`.
Для опросов с голосами заполните момент начала по имеющимся голосам; если голоса
раньше удалялись и установить факт начала невозможно, консервативно считайте
неопределённые старые опросы начатыми. Миграцию сначала проверьте на копии БД;
не выполняйте `ALTER` повторно без проверки схемы. Обычная установка 1.5 без
таблиц опросов получит полную новую схему при старте.

При удалении пользователя код явно удаляет его голоса, устройства и связанные
задания уведомлений, а также обнуляет ссылки автора/владельца новостей и медиа.
Это необходимо для существующих SQLite-установок с `foreign_keys=OFF`.
Не включайте глобально внешние ключи как побочное действие этого обновления:
изменение режима для старых таблиц требует отдельной проверки. Голосование,
закрытие и регистрация/отключение устройства повторно проверяют аккаунт после
ожидания блокировки, включая его поколение, чтобы запрос старого аккаунта не
записал данные после удаления и повторного использования ID.

## Порядок развёртывания

1. Уточните фактические каталог репозитория, commit, dirty-файлы, launcher,
   окружение Python, рабочий каталог процесса и `DATABASE_URL`. Исторически
   установка находилась в `C:\Users\User\Desktop\SavoyaApp\SavoyaApp`, а
   `backend_test_local.db` в её корне была рабочей БД, несмотря на имя.
   Сохраните именно используемые значения. `config.mdb` Gate — отдельная база.
2. Снимите приватный снимок текущих tracked/untracked-файлов сервера и их хешей,
   список изменений относительно Git, `.env`, зависимостей, launcher, текущих
   web-файлов/APK и конфигурации Nginx. Секреты не выводите в журнал и не коммитьте.
   В серверном checkout есть значимые локальные изменения; чистый Git-релиз не
   доказывает, что эти изменения включены.
3. В staging-копии сравните серверные файлы с выпуском и перенесите проверенные
   изменения с разрешением конфликтов. Сохраните локальные исправления Gate,
   настройки запуска, приватные ключи, media и БД. Не применяйте `git reset --hard`,
   `git clean` или полную замену серверного дерева. Результат слияния должен быть
   просмотрен и проверен до замены рабочих файлов.
4. Сделайте согласованную резервную копию SQLite через backup API либо копию
   после штатной остановки backend. Учитывайте WAL и связанные файлы. Медиа
   сохраняйте вместе с БД. Убедитесь, что копия читается; держите её вне Git и
   web-каталога. Не копируйте активный SQLite-файл обычной файловой операцией.
5. На копии данных примените стартовую миграцию и выполните проверки ниже с
   изолированными настройками, без команд реальному оборудованию Gate и без
   рассылки жителям. Сверьте количество аккаунтов/новостей/вложений, роли,
   сохранение существующих сессий и постоянный каталог медиа.
6. Определите реальный supervisor/службу/задачу запуска. Наличие
   `scripts/supervise_backend.ps1` само по себе этого не подтверждает.
   Согласуйте остановку через launcher, чтобы он не поднял старый backend
   посреди обновления. Установите проверенный backend и запустите его в прежнем
   окружении и рабочем каталоге; не создавайте конкурирующий процесс на порту.
7. Проверьте журнал старта, схему, `/health`, авторизованный API и права ролей.
   Затем установите web-сборку и подписанный APK 1.6.0/versionCode 17. Backend
   обновляется первым; до перехода клиентов избегайте новостей только с опросом.
   Не изменяйте без необходимости действующие Nginx, TLS, FCM, Gate и хранилище.
8. У APK проверьте `com.savoya.app`, рабочий HTTPS API `https://ipksavoya.ru`,
   встроенную конфигурацию Firebase и прежнюю подпись. Ожидаемый SHA-256
   сертификата: `2ffd21210907096d04e31a5a99c46431e9bb83d07be47a0de7cc55c8e6632ede`.
   Выполните обновление поверх установленной версии с сохранением данных.
   Зафиксируйте commit, хеш APK, результат проверки и фактический способ запуска.

## Откат

Предпочтителен исправляющий выпуск с сохранением данных и новых проверок прав.
Сначала остановите запись и разберитесь, какой слой вызвал проблему. Старый
web/APK можно вернуть с указанными ограничениями интерфейса; новые таблицы и
столбцы БД оставляйте на месте. Возврат кода, считающего любого `is_admin`
администрацией, снова даст диспетчеру лишние права.

**Нельзя откатывать проверку `auth_generation` после удаления аккаунтов и
возможного повторного использования ID.** Backend, игнорирующий поколение,
снова сможет принять JWT удалённого аккаунта для нового пользователя с тем же
ID. При откате сохраняйте исправленный модуль авторизации, выдачу поколений
новым аккаунтам, проверки ролей и очистку связанных данных; предпочтите
исправление вперёд. Простое восстановление старого commit этому не соответствует.

Не удаляйте новые таблицы/столбцы и не восстанавливайте устаревшую БД поверх
новых пользователей, голосов или новостей. Если восстановление резервной копии
всё же необходимо, отдельно согласуйте потерю/перенос записей после снимка и
согласованность с медиа и Gate. Смена JWT-секрета или массовое обнуление поколений
не являются штатной частью обновления либо отката.

## Проверка выпуска

- Выполнить backend-тесты на отдельной БД: `python -m pytest backend/tests`.
  Проверить frontend: `npm run typecheck`, `npm run test:news`,
  `npm run test:notifications`, `npm run test:dates`, `npm run test:roles`.
  Успех unit-тестов не подтверждает рабочую
  установку, Gate или физическую доставку push.
- На копии старой БД проверить повторный старт миграции, сохранение ролей,
  существующего JWT без поколения и данных. Проверить новые аккаунты с поколением;
  после удаления и повторного использования ID старый JWT должен получить 401.
- Житель и диспетчер читают и голосуют; публикация/правка/удаление, загрузка
  медиа, закрытие опроса, создание аккаунтов и управление сотрудниками для
  диспетчера получают 403. Без сессии — 401. Заблокированный аккаунт получает 401.
- Администрация создаёт сотрудников, меняет их роли и управляет жителями.
  Проверить запреты на удаление сотрудника, собственную блокировку/понижение,
  отключение последнего администратора и одновременное взаимное понижение.
- Проверить создание опроса с текстом/медиа и без них, ограничения вариантов,
  повтор публикации, смену ответа, повтор голоса и отсутствие имён голосующих.
  До голосования изменить варианты и отклонить голос со старым ID.
- После первого голоса проверить запрет изменения/удаления опроса при доступной
  правке текста/медиа. Удалить все тестовые аккаунты проголосовавших: суммы
  уменьшатся, определение останется заблокированным. Проверить закрытие и
  повтор закрытия, голос после закрытия, удалённый пост и параллельные запросы.
- Проверить удаление аккаунта с устройством и голосами, отсутствие наследования
  новому аккаунту, запрос голоса/устройства, ожидавший удаления, и закрытие
  опроса после отзыва административной роли. Повторные операции с опросом не
  должны создавать дополнительные задания уведомлений.
- В браузере проверить узкий телефонный и широкий desktop-экран, длинные
  варианты/вопросы, клавиатуру, редактор, архив, состояния загрузки/ошибки и
  реальную смену ролей без перезапуска приложения.
- На точном подписанном APK проверить обновление поверх предыдущей версии,
  вход/сохранённую сессию, опросы, медиа и переход по уведомлению. Доставку FCM
  на физическом телефоне и работу реальных пропусков/шлагбаумов/калиток отмечать
  отдельными результатами после развёртывания; `/health` их не подтверждает.
