# Новости и нижняя панель — 1.5.0 (Android versionCode 16)

Приложение открывается на последней новости. Нижняя панель: шлагбаумы, калитки,
мои пропуска и новости. Создание пропуска находится в разделе пропусков.
Председатель использует существующую роль администратора; публикация и изменение
новостей проверяются на сервере. Архив загружается порциями.

## Сервер

Проверенная 25 сентября 2026 года установка Windows находится в
`C:\Users\User\Desktop\SavoyaApp\SavoyaApp`. Рабочая база приложения — SQLite-файл
`backend_test_local.db` в этом каталоге. Несмотря на слово `test` в имени, это
существующая база установки: не заменяйте её новой базой и не меняйте `DATABASE_URL`
при обновлении. База Gate `config.mdb` для новостей не используется.

1. Перед обновлением сохраните согласованную резервную копию SQLite через SQLite
   backup API либо при остановленном backend. Обычное копирование работающей базы
   не гарантирует согласованность. Сохраните также `.env`, текущий APK и каталог
   медиа; резервные копии и секреты храните вне Git и web-каталога.
2. Сохраните список установленных пакетов и установите `backend/requirements.txt`
   в окружение действующего backend. В проверенной установке это Python 3.12.0 x64,
   отдельно от 32-битного Python для Gate. Pillow и google-auth отсутствовали;
   Pillow нужен для запуска нового backend даже без push. Pin `requests==2.33.1`
   сохраняет уже установленную серверную версию без понижения; локальный полный
   набор backend-тестов проверен с этой версией.
3. Задайте `NEWS_MEDIA_DIR` — постоянную приватную папку с абсолютным путём,
   например `C:/ProgramData/Savoya/news-media`. Это предлагаемое новое расположение,
   а не обнаруженная папка сервера. Не размещайте медиа в `frontend/dist` или
   каталоге заменяемой сборки. Учётной записи backend нужны права чтения/записи
   в папке медиа и временной папке загрузок, а также свободное место для файлов.
4. После обновления кода, зависимостей и `.env` перезапустите действующий backend
   его штатным способом, сохранив рабочий каталог, окружение и учётную запись.
   От рабочего каталога зависят относительный путь SQLite и загрузка `.env`.
   Перезагрузка Nginx не перезапускает Python и не применяет настройки FCM.
   Не запускайте второй backend на том же порту.
5. При старте создаются отсутствующие таблицы `news_posts`, `news_media`,
   `news_devices`, `news_notifications`; на момент проверки их не было.
   `create_all` не изменяет столбцы уже существующей ранней схемы News:
   если News ранее частично устанавливались, сначала сверьте схему и подготовьте
   её миграцию. Новости и медиа резервируйте вместе с базой приложения.
6. Обновите Nginx по конфигурации `deploy/nginx/savoyaapp-domain.conf`:
   `/api/` использует `^~`, лимит 101 MiB с учётом multipart, тайм-ауты 300 секунд,
   отключена буферизация запроса. В проверенной установке активный файл расположен
   в `C:/Users/User/Downloads/nginx-1.29.8/conf/nginx.conf`. Сохраните его реальные
   пути `root` и TLS-сертификатов: пример `E:/savoya/...` из шаблона не соответствует
   этой установке. Сохраните также ограничения проверки сессии для старых клиентов.
   Затем проверьте `nginx -t` и перезагрузите конфигурацию.
7. Из каталога `frontend` экспортируйте web-клиент
   (`npm ci`, `npx expo export --platform web --output-dir dist`).

Способ автозапуска проверенной установки пока не подтверждён. Наличие
`scripts/supervise_backend.ps1` не доказывает, что этот сценарий используется.
Перед перезапуском определите действующий launcher по процессу, службе или задаче
планировщика. Если используется этот supervisor, согласуйте остановку и запуск
через него: он следит за портом 8000 и после завершения backend запускает его снова.
Остановка только дочернего Python может привести к его запуску во время обновления.
Сохраните существующие параметры `RepoRoot` и `PythonExe`; не меняйте запуск GateTerm.

После перезапуска проверьте журнал старта, `/health` и авторизованный
`GET /api/news`, затем публикацию/чтение новости и загрузку файла. Успешного `/health`
недостаточно для проверки нового API, прав доступа и хранилища медиа.

До 10 вложений на пост, 100 MiB на файл. Фото получают уменьшенное превью;
в галерее полный оригинал загружается только для выбранного фото, соседние
страницы используют превью. Повторяющиеся проценты загрузки не перерисовывают редактор.
Видео передаются с поддержкой HTTP Range без автоматического воспроизведения.
Произвольные документы отдаются как скачиваемые файлы, активное содержимое
не исполняется на домене приложения. Ссылки на вложения подписаны и действуют час.
Обновление новости обновляет ссылки. Неприкреплённые загрузки очищаются через сутки.
Изменение записи проверяет её версию; повтор публикации с тем же request_id
не создаёт второй пост и вторую очередь уведомлений.

## Уведомления Android

Нужен Firebase-проект с Android-приложением `com.savoya.app` и включённым FCM HTTP v1.
В проверенной установке настройки и файлы Firebase не обнаружены. До их подключения
и проверки на телефоне доставка push не подтверждена.

- Для сборки задайте `SAVOYA_GOOGLE_SERVICES_FILE` — путь к `google-services.json`.
  Можно разместить файл в `frontend/google-services.json` (исключён из Git).
- На сервере задайте `NEWS_FCM_SERVICE_ACCOUNT_FILE` — путь к JSON сервисного аккаунта
  Firebase с разрешением отправки FCM. Файл хранится вне репозитория и web-каталога.
- `NEWS_FCM_PROJECT_ID` необязателен, по умолчанию используется project_id из файла.
  Если задаёте его явно, используйте строковый **ID проекта**, а не числовой
  номер проекта / sender ID. Оба JSON-файла должны относиться к одному проекту.
- Нужен исходящий HTTPS с сервера к Google OAuth и FCM. Мобильное устройство должно
  иметь Google Play Services, доступ к FCM и разрешение уведомлений.

JSON сервисного аккаунта с приватным ключом не включайте в APK, Git или каталог
web-клиента. Стандартные имена `*firebase-adminsdk*.json` и `*service-account*.json`
исключены из Git, но основной способ хранения — отдельная приватная папка.
Конфигурация Android `google-services.json` используется только при сборке;
добавление файла после установки APK не подключает Firebase в уже собранном приложении.
Вариант `SAVOYA_BUILD_VARIANT=preview` намеренно отключает FCM и использует другой
пакет: для проверки настоящих уведомлений нужен основной пакет `com.savoya.app`.

Регистрация устройства происходит после входа; настройки уведомлений доступны
в аккаунте. Выход удаляет регистрацию устройства. Новая публикация создаёт
сохранённые задания для активных устройств; правки повторно не уведомляют.
При отсутствии конфигурации сервер не сообщает об успешной доставке.
Успех публикации новости сам по себе не подтверждает доставку уведомлений.
Нажатие уведомления открывает соответствующую новость после входа.
Web-клиент имеет полный доступ к новостям; системные web-push в эту версию не входят.

Для Docker медиа сохраняются в именованном томе `news_media`; приватный JSON
сервисного аккаунта следует отдельно смонтировать read-only и указать его путь
внутри контейнера в `NEWS_FCM_SERVICE_ACCOUNT_FILE`.

## Подписанный APK

Используйте прежний ключ подписи приложения. Нужны переменные окружения
`SAVOYA_RELEASE_STORE_FILE`, `SAVOYA_RELEASE_STORE_PASSWORD`,
`SAVOYA_RELEASE_KEY_ALIAS`, `SAVOYA_RELEASE_KEY_PASSWORD`.
Пароли не записываются в исходники или build.gradle.

Из корня репозитория: `powershell -File scripts/build_android_release.ps1`.
Требуются JDK 17 и Android SDK для Expo SDK 51. Сценарий проверяет наличие
настройки Firebase; `-AllowWithoutPush` предназначен только для явно выбранной
сборки без push. Без ключа release-сборка не подменяет подпись отладочным ключом.

Перед распространением проверьте сертификат APK через `apksigner verify --print-certs`,
сравните его с установленной версией и выполните установку поверх неё с сохранением
данных. Рабочий серверный APK проверен: `com.savoya.app`, версия 1.4.0, код 15.
SHA-256 сертификата — `2ffd21210907096d04e31a5a99c46431e9bb83d07be47a0de7cc55c8e6632ede`;
сохранённый серверный ключ подписи соответствует ему. APK, ранее сохранённый
в репозитории как `release-1.0.11`, внутри имеет
versionName 1.0.10/versionCode 11; версия должна определяться по манифесту APK.

## Проверка перед выпуском

- `python -m pytest -q backend/tests`, `npm run typecheck`, `npm run test:news` и
  `npm run test:notifications` (6 проверок с имитацией Android/FCM: тайм-ауты,
  выход из аккаунта, запоздалые ответы и смена учётной записи).
  Клиентские сценарии и границы проверок описаны в `frontend/tests/NEWS_TEST_MATRIX.md`.
- Войти жителем: последняя новость, архив, фото, видео, скачивание документов;
  кнопок публикации и редактирования нет.
- Войти председателем: добавить несколько типов файлов, проверить прогресс,
  отмену/повтор загрузки, публикацию, редактирование и удаление.
- На телефоне: разрешить уведомления, закрыть приложение, опубликовать новость
  с другого устройства, открыть её через уведомление. Проверить выход из аккаунта.
- Убедиться в работе прежних пропусков и проходов на рабочем сервере.

Локальные тесты не подтверждают доставку FCM, доступность рабочего сервера,
совместимость подписи с текущим установленным APK или реальное управление Gate.
